# QuestRAG 技术方案文档

> 目标：这份文档不是单纯记录代码，而是把项目讲成“我理解业务问题 -> 我设计方案 -> 我做了验证 -> 我知道取舍和下一步”的面试表达材料。

## 1. 项目定位

用 1-2 句话说明这个项目解决什么问题。

> QuestRAG 是一个面向就业政务场景的 RAG 智能问答系统，用来回答就业政策、办事流程、岗位匹配等问题。系统通过知识库检索增强大模型回答，目标是减少大模型幻觉，让回答尽量有来源、有依据、可追溯。


## 2. 业务背景与问题

### 2.1 业务场景
> QuestRAG 定位在就业政务问答场景.面向的用户可能是求职者,就业政策咨询者,就业业务服务工作人员或者运营人员等,他们可能会查询就业政策,办事流程,就业岗位及联系方式等信息.
这类问题的特点是答案必须基于权威资料,并且资料具有地区性和时效性,需要即时维护更新.
因此系统需要把公开政策文件,岗位数据和其他维护的资料整理进知识库,增强大模型的检索生成,并在没有资料依据时拒绝回答或提示资料不足.

### 2.2 原始痛点

#### 政策资料分散
> 就业政策资料比较分散,用户想查就业登记,失业登记,创业政策时需要在多个网站页面,通知,办事指南或者PDF中去找,成本高.
#### 政策文本难读
> 政策文本通常篇幅长,表达正式,普通用户很难快速判断"我是否符合条件","需要准备什么材料","去哪里办理".
#### 办事咨询重复度高
> 服务窗口或者线上回复总是反复回答类似的问题,比如办理流程,材料需求,办理地点时间,联系方式等.
#### 人工维护成本高
> 一些FQA,岗位数据,窗口信息比如联系方式,地点等需要人工持续整理,且单靠人工帮助查询和回复效率较低

### 2.3 项目目标

- 准确回答就业政务相关问题。
- 回答尽量基于知识库，不知道就拒答或提示缺少资料。
- 支持知识库更新维护,数据源拓展。

## 3. 数据源设计

### 3.1 数据来源分类

| 数据类型 | 来源 | 示例 | 获取方式 | 可信度 | 更新频率 |
|---|---|---|---|---|---|
| 公开政策文档 | 人社局/政府官网 | 就业登记政策、创业担保贷款政策 | 手工整理/爬取 | 高 | 不定期 |
| 公开岗位数据 | 招聘网站/公开岗位表 | 岗位名称、要求、地点、薪资 | 手工整理/爬取 | 中 | 高频 |
| 运营维护资料 | 后台人工录入 | 电话、地址、办理材料、常见问题 FAQ | 后台录入/文档上传 | 高 | 高频 |

### 3.2 数据进入知识库流程

```text
原始资料 -> 清洗 -> 分块 -> 生成向量 -> 入库 -> 检索 -> 大模型生成回答 -> 来源校验
```

### 3.3 当前数据源准备情况
#### 已经准备
就业登记,失业登记办理流程说明,来源是政府官网,并且已经进入知识库
#### 当前缺少
缺少创业贷款政策,岗位数据,窗口信息等.

## 4. 语料清洗方案

### 4.1 为什么要清洗
- 无关页眉页脚空格影响向量化
- 可能存在重复内容,影响召回
- 可能存在内容格式混乱,需要统一修复格式

### 4.2 清洗规则

| 清洗项 | 做法 | 原因 |
|---|---|---|
| 去除无关符号 | 去掉页码、页眉页脚、水印、重复空行、无意义符号、OCR 乱码等 | 减少噪声，避免无关内容进入向量库，影响检索结果 |
| 保留标题层级 | 保留一级标题、二级标题、政策名称、小节名称，并在分块时带入 chunk metadata 或正文前缀 | 标题能提供上下文，避免单个 chunk 丢失所属政策或条款含义 |
| 保留政策条款编号 | 保留“一、二、三”“第 X 条”“（一）（二）”等编号 | 条款编号有助于定位原文，也方便回答时说明依据 |
| 表格转文本 | 将表格转成结构化文本，例如“材料：身份证；要求：原件及复印件” | 表格直接解析容易乱序，转成文本后更利于检索和大模型理解 |
| 去重 | 对重复段落、重复政策说明、重复 FAQ 进行去重或合并 | 避免相同内容多次召回，影响排序和回答质量 |

## 5. 分块策略
### 5.1 为什么不能整篇入库

- 文档太长时，单个 chunk 会包含多个主题，所有内容都会被压缩到一个固定维度的向量中，导致向量表达的语义过于宽泛，更偏向整体大意，局部关键细节容易被稀释。
- 用户问题通常只对应文档中的某一小段内容，例如申请条件、材料清单、办理流程或补贴期限，整篇入库会降低检索命中的精准度。
- 分块过大可能召回大量无关信息，污染上下文，降低大模型回答质量，同时增加上下文 token 成本。
- 分块过小又可能丢失必要上下文，例如只保留“最长不超过两年”，但不知道对应的是哪个政策、哪类补贴。

### 5.2 候选策略对比

| 策略 | 做法 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|---|
| 固定长度分块 | 按字符/token 长度切 | 简单稳定 | 按长度切，不按语义切,可能切断语义 | 普通文本 |
| 按标题/段落分块 | 根据 markdown 标题、段落切 | 保留语义结构 | 文档格式不规范时效果差 | 政策文档 |
| 递归分块 | 标题 -> 段落 -> 句子逐级切 | 兼顾结构和长度 | 实现稍复杂 | 长政策文档 |
| 问答对分块 | 一条问题答案作为一个块 | 精准可控 | 依赖人工维护 | FAQ/运营资料 |

### 5.3 当前选择

当前项目先使用固定长度分块策略。原因是项目早期文档数量较少、篇幅较短，优先目标是快速打通“文档上传 -> 切分 -> 向量化 -> 检索 -> 问答”的基础流程，因此先采用实现成本较低的普通分块方式。

目前这个策略存在两个问题：

1. 语义切分不完整  
   固定长度分块可能把一个完整政策条款切开，例如申请条件、材料要求或办理流程被拆到不同 chunk 中，导致单次检索拿到的信息不完整。

2. 检索和回答效率下降  
   因为单个 chunk 信息不完整，系统可能需要依赖多次检索或召回更多 chunk 来补齐上下文，增加检索和大模型上下文成本，也可能影响回答质量。

下一步计划根据政策文档的实际结构优化分块策略，优先按政策名称、标题层级、条款、段落等语义单元进行切分。目标不是单纯把 chunk 切得更小，而是在控制 chunk 大小的同时，尽量保证每个 chunk “小而完整”，既保留必要上下文，又减少无关信息。

## 6. 检索方案

### 6.1 基础向量检索

流程：

```text
用户问题 -> 问题向量 -> 向量库相似度计算 -> top_k 召回 -> 作为上下文给大模型
```

当前实现：

- embedding 模型：BGE-M3，输出向量维度为 1024。
- 向量存储：当前未接入独立向量数据库，先使用内存列表保存文档 chunk 和 embedding，用于快速验证 RAG 流程。
- top_k：当前召回 4 个相关 chunk。
- 相似度算法：使用余弦相似度计算用户问题向量和文档 chunk 向量之间的相似度。
- 当前问题：向量检索更适合语义匹配，但对手机号码、政策编号、具体地址、窗口名称等精确值检索不够稳定。如果用户问题依赖精确字段，纯向量检索可能召回不准或排序靠后。

### 6.2 关键词检索

为什么需要关键词检索：

- 电话、编号、地点、政策名、办理材料等精确词，向量检索不一定稳定。
- 用户问题很短，或者问题中包含明确关键词时，关键词命中可能比纯语义匹配更直接。
- 关键词检索可以作为向量检索的补充，提高精确字段类问题的召回能力。

当前实现：

- 关键词提取方式：英文、数字、编号等按完整 token 提取；中文内容按 2 字滑动窗口提取关键词。
- 打分方式：根据用户查询是否完整命中、关键词覆盖情况、关键词重复出现次数进行打分。其中完整 query 命中得分最高；关键词命中会增加得分；重复出现会给予有限奖励，避免单个词重复刷高分。
- 当前问题：
  - 关键词提取方式比较粗糙，中文按 2 字滑窗容易产生无意义关键词，也可能切碎真正的业务词。
  - 当前匹配方式主要是字符串包含匹配，缺少分词、同义词、停用词、字段权重等处理，容易引入召回噪声。
  - 当前打分规则是经验规则，还没有通过评测集验证。
- 后续优化：
后续计划将当前内存向量库和手写关键词匹配逐步替换为 Elasticsearch。Elasticsearch 同时支持 BM25 关键词检索和 dense_vector 向量检索，因此可以在一个检索组件中完成关键词召回、语义召回和混合排序。

设计上，每个 chunk 入库时同时保存：
- 原文内容
- metadata，例如文档来源、标题、条款编号、chunk_id
- embedding 向量字段

查询时：
1. 对用户问题生成 query embedding。
2. 使用 Elasticsearch 的 BM25 检索召回关键词相关结果。
3. 使用 dense_vector / kNN 检索召回语义相关结果。
4. 对两路结果进行融合排序，例如加权融合或 RRF。
5. 返回 top_k chunk 给大模型生成回答。


### 6.3 混合检索

设计思路：

```text
向量检索结果 + 关键词检索结果 -> 去重 -> 统一打分 -> 排序 -> top_k
```

当前权重：

```text
final_score = vector_score * 0.6 + keyword_score * 0.4
```

为什么这么设：

- 向量检索负责语义相关。
- 关键词检索补充精确匹配。
- 权重需要后续通过评测集调整。

## 7. 结果校验与幻觉治理

### 7.1 要解决什么问题

RAG 并不天然保证大模型一定按知识库回答。即使 top_k 检索出了资料，大模型也可能：

- 没用检索结果。
- 自己补充不存在的信息。
- 把多个片段拼错。
- 对没有依据的问题强行回答。

### 7.2 当前已做

- 检索结果阈值：0.75
- top_k：3
- 拒答策略：当前只是使用提示词约束，当未检索到可信资料时，进行拒答，但过于依赖大模型。
后续将记录检索工具使用次数，检索结果等，拒答策略将根据多次检索后的整体证据进行评判
- 当前遇到的问题：未做来源校验，大模型可能编造无来源和资料根据的回复，需要确保大模型回复基于检索资料，保证资料来源有效。

### 7.3 重要教训

> 之前把检索校验阈值设为 0.75，结果导致很多可用资料被全部过滤掉。后来临时提高 top_k，并将阈值降到 0.4，先恢复可用性。这说明阈值不能凭感觉设置，必须结合评测集验证。

### 7.4 下一步方案

| 方案 | 作用 | 优点 | 风险 |
|---|---|---|---|
| 来源 id 校验 | 检查回答引用是否来自知识库记录 | 可追溯 | 需要结构化返回 |
| 二次相似度匹配 | 检查回答和原文是否相似 | 工程可落地 | 阈值需要调 |
| 拒答策略 | 检索不到时不强答 | 减少幻觉 | 可能降低回答覆盖率 |
| 评测集回归 | 用固定问题反复测试 | 可量化 | 需要维护数据 |

### 7.5 面试表达

> 我对 RAG 幻觉的理解不是简单靠提示词解决。提示词不是强约束，temperature 也只是影响输出随机性，不能保证答案来自知识库。所以我会从工程上做来源校验，比如让检索片段带 id，生成回答时引用 id，再回查这个 id 是否真实存在。同时用评测集观察召回率和回答准确性。
