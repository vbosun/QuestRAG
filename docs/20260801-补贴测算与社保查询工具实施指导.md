# QuestRAG 补贴测算与社保查询工具实施指导

> 目标：在 QuestRAG 现有政务 RAG 问答、岗位检索、登录认证、权限体系基础上，新增“社保查询”和“补贴测算”两个工具。社保查询使用模拟社保库提供本人数据查询；补贴测算以用户自然语言输入为主入口，结合用户画像、社保数据、政策规则库和政策原文 RAG，输出可解释、可追溯、可复核的测算结果。

## 1. 核心结论

这两个工具不要做成纯提示词问答。

推荐架构：

```text
自然语言输入
  -> 大模型识别意图和抽取信息
  -> 社保查询工具读取模拟社保数据
  -> 补贴匹配/测算工具执行确定性规则
  -> RAG 检索政策原文提供依据
  -> 大模型组织解释、追问缺失信息、生成办理建议
```

关键边界：

```text
社保查询 = 结构化模拟数据查询
补贴测算 = 规则引擎计算 + RAG 依据解释
大模型 = 交互、意图识别、字段抽取、解释，不负责直接“猜金额”
```

一句话原则：

```text
RAG 找依据，规则引擎算结果，LLM 做交互和解释。
```

## 2. 产品交互定位

主入口不是“用户先选择补贴名称”，而是自然语言输入。

用户可以直接问：

```text
我毕业两年没工作，自己交社保能领补贴吗？
我是灵活就业人员，社保交了 8 个月，能补多少钱？
我开了个小店，能不能申请创业补贴？
帮我查一下我的社保缴费记录。
我的养老保险交了多少个月？
```

系统流程：

```text
用户自然语言输入
  -> 判断是社保查询、补贴测算、政策解释、岗位查询还是其他
  -> 如果是社保查询：调用 social_security_search
  -> 如果是补贴测算：
       1. 抽取用户描述里的条件
       2. 读取登录用户画像
       3. 查询模拟社保数据
       4. 匹配候选补贴
       5. 发现缺失字段则追问
       6. 字段足够则调用规则引擎测算
       7. 用 RAG 检索政策依据
       8. 返回结果、依据、材料、办理建议
```

辅助入口可以有“补贴清单”，但不是主流程：

```text
政务工具
  - 社保查询
  - 补贴测算

补贴测算页
  - 输入你的情况
  - 系统推荐可能适用的补贴
  - 点击某项补贴继续精细测算
```


## 6. 补贴测算设计

补贴测算是重点，不能只做向量检索。

### 6.1 补贴测算流程

```text
用户输入个人情况
  -> LLM 判断为补贴测算
  -> LLM 从用户话语中抽取显式条件
  -> subsidy_match 读取用户画像和社保数据
  -> 匹配候选补贴规则
  -> 如果缺字段，返回 missing_inputs
  -> LLM 追问用户
  -> 用户补充信息
  -> subsidy_calculate 对候选补贴执行规则引擎
  -> retrieve_context 检索政策原文依据
  -> LLM 组织最终回答
```

多轮示例：

```text
用户：我毕业两年没工作，自己交社保能领补贴吗？
系统工具：
  - 查询社保：缴费 8 个月，灵活就业缴费
  - 匹配候选：高校毕业生灵活就业社保补贴、就业困难人员灵活就业社保补贴
  - 缺失字段：是否高校毕业生、毕业时间、是否已做就业登记
助手追问：
  你是否为高校毕业生？毕业时间是哪一年？目前是否已办理就业登记？

用户：我是 2025 年毕业的，已经做了灵活就业登记。
系统：
  - 调用 subsidy_calculate
  - 返回是否符合、预计金额、计算过程、依据
```

### 6.3 规则结构

规则必须结构化，避免让 LLM 直接解释公式。

示例：灵活就业社保补贴。

```json
{
  "target_tags": ["flexible_employment", "employment_difficulty_person"],
  "required_inputs": [
    {
      "field": "employment_status",
      "label": "就业状态",
      "source": "user_profile",
      "required": true
    },
    {
      "field": "social_insurance_months",
      "label": "社保缴费月数",
      "source": "social_security",
      "required": true
    },
    {
      "field": "actual_social_insurance_payment",
      "label": "实际社保缴费金额",
      "source": "social_security",
      "required": true
    }
  ],
  "conditions": [
    {
      "field": "employment_status",
      "op": "eq",
      "value": "flexible_employment",
      "message": "需为灵活就业状态"
    },
    {
      "field": "social_insurance_months",
      "op": ">=",
      "value": 6,
      "message": "社保缴费需满 6 个月"
    },
    {
      "field": "person_tags",
      "op": "contains_any",
      "value": ["employment_difficulty_person", "college_graduate_within_2_years"],
      "message": "需属于就业困难人员或离校 2 年内高校毕业生等政策对象"
    }
  ],
  "formula": {
    "type": "ratio_cap",
    "base_field": "actual_social_insurance_payment",
    "ratio": 0.6667,
    "max_months": 36,
    "amount_round": 2
  },
  "materials": ["身份证", "社保卡", "灵活就业登记材料", "社保缴费凭证"],
  "process_steps": ["线上或窗口申请", "经办机构审核", "公示", "补贴发放"]
}
```

### 6.4 条件操作符

第一阶段实现这些操作符即可：

```text
eq
neq
in
not_in
>=
>
<=
<
contains
contains_any
between
exists
```

条件执行结果要返回：

```text
field
label
passed
actual_value
expected_value
message
```

### 6.5 公式类型

第一阶段实现三种公式：

```text
fixed_amount
  固定金额，例如一次性补贴 1000 元

ratio_cap
  按实际缴费/基数比例计算，可设置上限月数

range_amount
  金额区间，仅能输出估算区间
```

公式执行必须返回计算过程：

```json
{
  "estimated_amount": 2240.0,
  "amount_unit": "元",
  "formula_label": "实际缴费金额 × 2/3",
  "calculation_steps": [
    "实际社保缴费金额：3360 元",
    "补贴比例：2/3",
    "预计补贴金额：3360 × 0.6667 = 2240 元"
  ],
  "max_months": 36
}
```

```text

```

```python
def match_subsidies(profile: SubsidyUserProfile, question: str | None = None) -> list[SubsidyMatchResult]:

```

匹配结果：

```python
class SubsidyMatchResult(BaseModel):
    policy_id: str
    policy_name: str
    category: str
    match_status: Literal["eligible", "possible", "not_eligible"]
    match_score: float
    passed_conditions: list[ConditionResult]
    failed_conditions: list[ConditionResult]
```

匹配规则：

```text

possible      有候选政策，但缺少关键字段
not_eligible  硬性条件明确不满足
```

自然语言问题用于缩小候选范围：

```text
用户提到“毕业”“高校” -> 优先高校毕业生相关补贴
用户提到“自己交社保”“灵活就业” -> 优先灵活就业社保补贴
用户提到“开店”“创业” -> 优先创业补贴/创业担保贷款
```

注意：语义识别只用于候选排序，不用于最终资格判断。

### 10.3 工具调用顺序建议

```text

2. 如果 missing_inputs 非空，先追问
3. 用户补充后 subsidy_calculate
4. retrieve_context 检索政策依据
5. 回答中用引用编号标注政策条件和材料依据
```

不要让 LLM 不调用 `subsidy_calculate` 就直接报金额。

## 11. 政策原文 RAG 与规则库关系

政策原文仍然进入知识库：

```text
documents / vector backend
```

规则库存结构化模型：

```text
subsidy_policy / subsidy_rule
```

二者通过：

```text
subsidy_policy.source_doc_id
```

关联。

回答时：

```text
金额、资格判断 -> 来自规则引擎
政策条件、材料、流程解释 -> 通过 retrieve_context 找原文依据
```

如果规则库和政策原文冲突：

```text
优先提示“规则与政策原文可能不一致，请管理员核对”
不要悄悄输出确定结论
```

## 20. 执行注意事项

1. 不要让 LLM 直接根据政策文本猜金额。
2. 不要把社保查询做成全库检索，第一阶段只能查本人。
3. 不要在日志里打印完整身份证号、社保号、token。
4. 不要把“用户选择补贴”作为唯一入口，自然语言输入才是主入口。
5. 不要把补贴规则只写在 prompt 中，必须结构化入库。
6. 不要把缺失字段写死在前端，前端应根据 `missing_inputs` 动态生成。
7. 不要一次追求覆盖所有补贴，先做 2-3 个样板闭环。
8. 不要让政策原文和规则库脱节，规则要关联 `source_doc_id`。
9. 不要忽略免责声明，测算结果必须说明以经办机构审核为准。
10. 不要把社保工具返回的敏感明细无节制塞进 LLM 上下文。
