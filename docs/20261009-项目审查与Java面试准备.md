# QuestRAG 项目审查与 Java 面试准备

审查日期：2026-10-09。目标：稳定 2026-10-10 的面试演示，并给出可以实际验收的成熟化路线。根据本地代码、测试、当前服务和历史数据库记录判断；岗位依据用户提供的招聘截图。没有做全系统压测，没有验证真实政务平台，没有把一次演示成功解释为生产可用。

后续部署更新：同日新增 Linux Docker Compose，已经连接已有 Ollama Embedding 并完成真实政策检索、来源显示和申请草稿验证。以下最初审查记录中的 Embedding 阻塞及“尚未容器化”属于当时状态；最新验收与限制见 [Linux 部署记录](linux-docker-deployment.md)。

## 1. 结论

**项目方向没有脱离现实，但成熟度仍是业务应用原型。** 它已经超过单纯“接模型做聊天”：有文档管理、检索策略、评测、权限、会话持久化、确定性业务工具、申请草稿和人工核对。主要缺口集中在业务一致性、异步任务恢复、可观测性、环境复现与安全边界。

**对明天高级 Java 岗，最大的匹配问题是这个仓库没有 Java 实现。** Python 项目可以展示系统设计和主动学习，但不能单独证明 Spring、MySQL 调优、Java 并发、Netty 或消息队列的实战水平。应先讲自己的真实 Java 经历，再用本项目证明业务建模、数据安全和工程取舍；不要包装成“Java AI 平台”。

今晚的高收益选择：稳定演示、准备工程问题的答案、整理真实项目经历和可验证数据。不要为招聘关键词仓促堆叠中间件，不承诺无法证明的并发量、准确率或节省成本。面试通过还取决于已有经验与问答表现，不能据此估算通过概率。

## 3. 当前架构与值得讲的设计

实际技术栈是 Python 3.12、FastAPI、LangChain Agent、React/TypeScript、PostgreSQL、Redis 和可切换的向量后端；当前环境使用 Milvus。变量 `OPENAI_*` 表示兼容 API 配置，当前生成供应商为 DeepSeek，不等于实际使用 OpenAI 模型。

主链路：前端携带登录身份 → 后端验证权限 → 构建当前用户可用的工具与检索范围 → 模型选择工具 → 工具执行检索或业务逻辑 → SSE 返回文本/引用/artifact → 会话与草稿保存在 PostgreSQL。办事 artifact 让前端打开独立模拟业务页面；预填与人工核对具有明确边界。

可以深入讲的点：

1. **RAG 与规则工具职责分开。** 政策解释依赖文档证据；金额和资格的演示测算由确定性规则处理。大模型不直接作为财务计算器，也不应自行确定正式资格。
2. **权限落在服务端。** 前端菜单隐藏只是体验，真正权限在 API、工具调用和检索过滤中检查。需要继续验证配置、映射发布和所有资源的边界，而不是因为“有登录”就声称安全。
3. **草稿和提交分开。** AI 协助填入已知值，缺少的信息不编造，最终提交由人核对。提交对外有副作用，必须有幂等与可追溯设计。
4. **检索参数可实验比较。** top_k、recall_k、分块和 RRF 可以用同一数据集对比，而不是凭直觉越大越好。
5. **状态真实性比动画重要。** 本次去掉虚假完成提示，用业务页回执证明实际填入，体现故障可解释和安全降级。

需要纠正的表述：Milvus 当前关键词分支使用 TEXT_MATCH/LIKE 匹配，匹配项 keyword_score 基本是固定值，并未实现 BM25 排名；它和向量结果做 RRF 不等于“BM25+向量+重排序全部完成”。会话历史存库也不等于 Agent 执行过程具备断点恢复。

## 4. 生产差距：按风险和收益排序

以下是静态审查发现，尚未全部修复。不应把这些路线写进简历作为已完成能力。

### 优先级 P1：接入真实数据或对外服务前

| 发现及代码依据 | 实际影响 | 建议与验收 |
|---|---|---|
| `applications/service.py:update_draft_field` 先读 revision、再调用 `store.py:upsert_field` 无条件写入 | 两个并发请求都通过旧版本检查，后写覆盖先写；当前“乐观锁”并非原子操作 | 使用带 revision 条件的 UPDATE/RETURNING 或锁定行；两个并发请求只能一个成功、另一个返回 409 |
| 创建申请、同步草稿和工作流推进分多次连接提交 | 中途失败可能留下半份草稿、完成的旧任务但未创建的新任务，审计与状态不一致 | 在一个事务里处理业务实体、字段、任务和审计；注入故障后全部回滚 |
| `page_connectors.py:analyze_page` 直接 urlopen，缺少目标网络与重定向校验 | 配置工具可能访问本机/内网或非业务地址，形成 SSRF；浏览器白名单不覆盖这一函数 | 统一 URL 策略、协议、允许域、解析 IP 与每次重定向校验；测试 file URL、内网地址与跳转绕过 |
| `page_connectors.py:save_connector` 用 business_code 拼接文件路径 | 包含路径分隔符/绝对路径的输入可能写出配置目录 | 校验固定标识格式并验证最终路径；遍历和绝对路径输入必须失败 |
| 映射配置直接保存为 published，审批主要依赖提示词 | 用户确认不是服务端状态约束，提示词不能替代发布授权 | 草稿→人工确认→发布的明确 API 状态机，版本和变更审计 |
| 文档过滤目前主要按 scope_code 分类，未实现用户/部门级文档 ACL | private_docs、department_docs 不是自动的本人/本部门隔离 | 使用 owner_id、department_id 或文档授权表做服务端检索前过滤，并验证跨用户/跨部门访问；演示数据不要当真实隐私数据接入 |
| `workflow_service.py:get_workflow_detail` 使用申请人本人访问检查 | 有审批权限的操作员仍无法处理其他申请人案例，多角色闭环不完整 | 根据申请人/候选审批人分别授权，合法审批可访问、无关用户不可访问，并验证拒绝与退回分支 |
| 独立模拟提交只返回模拟编号，材料不被持久接收 | 页面回执与 QuestRAG case 状态脱节；不代表办结，不可用于真实申请 | 真正对接时以受认证回调或业务 API 收据同步状态；提供幂等键、唯一收据、失败补偿，不凭前端文字改状态 |

优先修事务和原子版本校验，再完成一个真实的多角色业务闭环。这比追加十个工具更能证明高级后端能力。

数据库锁和并发一致性应按具体数据库机制选择。[PostgreSQL 锁文档](https://www.postgresql.org/docs/17/explicit-locking.html)可作为现有实现的参考；面试讨论 MySQL 时要明确其隔离级别与锁行为不同，不能直接套用 PostgreSQL 的细节。

### 优先级 P2：让服务能恢复、能测量、能复现

- **连接池与统一事务入口。** 当前 `rag/pg_store.py`、认证与权限存储反复创建 psycopg 连接；先合并数据访问约定与连接池，再基于实际查询和执行计划优化。不要先上缓存掩盖不合理 SQL。
- **健康与就绪检查。** `main.py` 一个大的初始化 try/except 会在失败后继续启动；部分核心能力可能不可用。区分进程存活与服务就绪，并检查 DB、Redis、检索和模型依赖的状态；模型检查宜低成本、按需或缓存，避免探活产生持续费用。
- **持久任务。** 评测 `run_evaluation` 在请求内执行长任务；浏览器会话、任务映射、worker TASKS/RUNNERS 在进程内。重启和多进程会丢状态。使用任务表、队列、lease/heartbeat、重试上限、取消和幂等，API 返回 task_id。引入 MQ 要解决这个具体问题。
- **执行恢复与副作用隔离。** PostgreSQL 聊天记录是文本记忆，不是工具执行的 checkpoint。需要恢复复杂 Agent 时再采用持久执行状态；无论框架如何，业务写入都必须有幂等键，防止恢复时重复提交。[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)明确区分图状态 checkpoint 与跨线程数据 store。
- **可观测性。** 记录 request_id、用户脱敏标识、工具名、检索文档版本、模型标识、耗时、token/成本和失败类别，避免记录明文密钥或完整个人资料。关注首字延迟、总延迟、P95、工具成功率、超时和错误率。当前没有这些负载测量，不能声称高并发稳定。
- **部署复现。** 添加脱敏配置模板、明确初始化与数据迁移、容器/Compose、备份恢复及 CI；先完成单机可重建，再讨论微服务或 Kubernetes。
- **前端加载。** 生产构建主 JS 约 2.63 MB（gzip 约 841 KB），可按聊天、评测、图表、权限页面做懒加载。sm-crypto 的 crypto 外部化是构建警告，登录实际成功，但仍需跨浏览器确认，不应仅提高警告阈值。
- **测试隔离。** 测试 DB/Redis/Milvus 应有专用命名空间，CI 单测不访问开发者实库。现有 `tests/test_rag.py` 部分测试会真实写向量集合，不能在当前知识库上直接当回归测试跑。

健康、审计、指标是成熟服务的常规组成；Java 实现可利用 Spring Boot Actuator 的相关能力，而当前 Python 服务也应达到对应目标。[Spring Boot 生产功能说明](https://docs.spring.io/spring-boot/reference/actuator/index.html)。

### 优先级 P2：提高检索与回答可信度

- 给政策加地区、生效/失效日期、来源 URL、版本和适用人群；查询时在服务端筛选，回答中明确来源时间。政务场景中“找到相似段落”不等于“当前政策有效”。
- 做向量、关键词和融合的同集对比。当前 Milvus 关键词结果缺少有意义的排序，可先验证排序式稀疏召回/BM25；只有证据表明有收益时再加 reranker。不要因为流行就增加调用成本。
- 区分检索评测与回答评测。前者看来源与证据、排序；后者看忠实性、关键点、拒答、引用是否支持对应断言。补充资料不足、过期政策、地区冲突、权限越界、工具失败和提示注入样本。
- 把评测集、知识库版本、模型标识、Prompt、配置和代码版本一起记录；固定比较口径，另外记录评分覆盖率/评分失败数，防止只有少数成功题看起来平均分很高。
- 办事定义返回的来源目前不一定进入文档引用收集链路。一次“就业登记材料”真实提问返回了模拟指南内容但 sources 为空；不能把它当作政策文档检索成功或权威政策引用。

离线回归和上线后的质量监测具有不同目的，二者都需要；可以参考 [LangSmith 评测类型说明](https://docs.langchain.com/langsmith/evaluation-types)，但没有必要为了明天演示临时采购或接入平台。

### 暂缓：没有明确问题和验收标准的复杂化

全量 Java 重写、微服务拆分、Kubernetes、多 Agent、模型微调、同时保留多套在线向量库，都不适合今晚做。现有需求下优先模块化单体、清晰事务、可靠任务和可解释评测。招聘截图列出的框架也不是项目必须全部采用的清单。

## 5. 历史评测能证明什么

审查时只读数据库看到 8 个知识文档、16 条评测运行、530 条评测题目结果。最近一条 completed 记录为 `eval_183753830d1f`，名称是“检索评测 2026/8/5 21:46:48”，共 40 题；这不是本次重跑。

| 指标 | 该记录值 | 应如何解释 |
|---|---:|---|
| 来源命中率 | 100% | 非拒答题检索命中了期望来源，不表示答案全部正确 |
| 证据命中率 | 94.29% | 依赖现有 evidence 匹配定义和样本标注 |
| MRR | 0.8369 | 反映期望结果的排序，不是回答质量 |
| 检索通过率 | 82.5% | 含现有拒答题统计口径，不能等同生产准确率 |
| 生成通过率 | 60% | 当前启发式关键点/引用/拒答规则，并非人工全面审核 |
| 生成错误数 | 4 | 应先分析错误，再谈提升策略 |
| 检索拒答命中率 | 0% | 代码把“检索返回空列表”算通过；不等同对话真实拒答行为 |
| 历史 RAGAS 平均值 | 0.6843 | 含 enabled 布尔值污染，本次修复前的聚合值不可作为新版质量证据 |

另外有历史记录显示 RAGAS average=1.0、实际 metric_averages 只有 enabled=1.0；这是统计错误，不能讲成“满分”。上述旧记录不被改写，后续应固定配置重跑并明确统计定义。检索调参、知识补全和评分失败排查应先于追求漂亮数字。

合适的面试表达：“我建立了检索与生成分开的评测流程，发现来源命中高不代表答案质量高，也发现并修正了统计把 enabled 当评分的问题。接下来要补难题、校准标注并记录评分覆盖率。”

## 6. 对两个岗位的匹配分析

### 明天重点：高级 Java / 航天测控后端

### AI 应用工程师岗位

RAG、LLM API、工具调用、Prompt、评测、业务落地与该岗位更直接匹配。弱项仍是企业部署、质量数据、线上恢复与容量证明；并没有因为依赖列表包含某库就具备框架深度。餐饮案例可以讨论门店 SOP、供应商制度、异常处理知识库；销量预测和排班优化需要相应数据与模型/约束算法，不能把问答包装成已实现预测优化。微调没有实际数据需求和效果对比时暂缓。

## 8. 最可能被追问的技术问题

1. **为什么 Java 岗做 Python 项目？** Python 用于快速验证模型生态；核心工程方法与语言无关，但 Java 实战应由真实工作经历支撑。未来可保留 Python AI 服务，Java 承接交易/审批等核心业务，无需全量重写。
2. **两个请求同时改草稿会怎样？** 当前先查后写存在丢更新。计划用 UPDATE ... WHERE revision = expected RETURNING，在同一事务中写审计；零行更新返回冲突，让用户重新读取。不能回答“现在已经有 revision 所以没问题”。
3. **创建申请和审计如何保持一致？** 本地事务内一起提交；跨系统通知用 outbox 和重试，远端必须幂等。消息发送不应和数据库提交做无约束双写。
4. **消息重复或用户重试怎么办？** 以业务幂等键和唯一约束保证只产生一次有效结果；重复请求返回已有任务/收据。消费侧重试、死信/人工处理与对账，不能简单保证“绝对不重复”。
5. **SQL 性能怎么排查？** 先观察慢查询和数据规模，读取执行计划、过滤选择性、排序/回表、锁等待，针对具体查询设计联合索引与分页；用相同数据与负载验证。列出真实 Java/MySQL 案例，不照搬本项目未测结果。
6. **Redis 挂了怎么办？** 当前认证依赖它，要明确可接受的登录与已有会话行为；缓存和认证故障策略不同。讲超时、连接池、过期和拒绝/降级，不能无条件绕过鉴权。
7. **SSE 与 WebSocket 怎么选？** SSE 用于后端单向推送生成文本；双向实时浏览器控制需要独立交互通道。连接中断不代表业务执行回滚，应把任务状态与连接状态分开。
8. **为什么 RRF？** 两种召回分数尺度不同，用排名融合可减少对分数归一化的依赖；结果仍受各自排名质量影响，当前关键词分支排序弱，需要评测验证。不能声称融合后必然更优。
9. **如何防幻觉？** 证据检索、资料有效性、引用支持检查、缺资料时拒答、规则计算、权限与评测共同约束；不存在仅靠 Prompt 保证零幻觉。
10. **如何控制模型成本与耗时？** 有上限的上下文、召回数量、模型步数和输出，按调用链统计 token/成本/失败，重试有预算。先测瓶颈，再缓存不含敏感数据且版本可失效的结果。
11. **Java 并发问题怎么讲？** 以真实线程池/锁/共享状态案例解释 happens-before、线程安全、队列容量和拒绝策略；数据库一致性不能靠单进程 Java synchronized 替代，多实例时仍需数据库或分布式方案。
12. **如果涉及 Netty 设备接入？** 讨论协议帧界定、粘包拆包、心跳、背压、断线重连、设备身份、事件时序与幂等；没有实际经验时说设计思路，别假装当前仓库实现了这些。

## 9. 面试后两周的建设路线

| 阶段 | 内容 | 可验证的完成标准 |
|---|---|---|

| 第 7～9 天 | 一键环境、迁移、任务持久化、健康检查、基础指标和 CI | 空测试环境可初始化；worker 重启能恢复或明确标记失败；指标可查 |
| 第 10～12 天 | 补地区/时效元数据，固定评测集，比较检索策略，校准评分 | 保存可复现实验和失败案例，评分失败不被算满分，不承诺先验提升 |

Java 模块建议只实现“申请任务创建与状态查询”这个垂直切片，通过 HTTP 调现有 Python AI 服务。它比只有转发接口的 Java 壳更有价值；后续有吞吐或解耦证据再引入 MQ。两周是建议时间箱，实际进度取决于可投入时间，未代表已经实施。
